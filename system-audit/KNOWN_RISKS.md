# PartnerLinks Known Risks

Purpose:

- Track reliability, attribution, payout, security, and UX risks that are known but not yet fully eliminated.
- Keep risk language precise and operational.

## Risk Severity

- `SEV0`: Active production integrity issue.
- `SEV1`: Could create wrong payouts, wrong attribution, duplicate money movement, or unauthorized mutation.
- `SEV2`: Could confuse operators/users or create unsafe assumptions before scale.
- `SEV3`: Documentation, workflow, or observability improvement.

## Active Risks

## Platform Abuse And Safety Risk Categories

Core safety principle:

```text
conversion_created does not mean safe_to_pay
```

No payout should be released just because a conversion exists. Payout eligibility requires:

- deterministic attribution.
- acceptable commerce quality.
- safe brand settlement/funding.
- refund/reversal handling.
- explicit payout eligibility.

### RISK-017 - Attribution Hijacking / Cookie Stuffing

- Severity: `SEV1`
- Category: `ATTRIBUTION_HIJACKING`
- Status: `WATCH`
- Description:
  - Bad actors may try to set attribution without genuine referral intent.
- Examples:
  - cookie stuffing.
  - forced attribution.
  - invisible click/cookie injection.
- Current prevention:
  - deterministic `partnerlinks_ref`.
  - Shopify cart/order attributes.
  - exact attribution before fallback.
  - no payout from raw click/cookie alone.
  - ambiguous attribution skips.
  - diagnostics for skipped/unmatched attribution.
- Regression rule:
  - Ambiguous attribution cannot create a conversion or payout.

### RISK-018 - Last-Click / Extension / Coupon Attribution Theft

- Severity: `SEV1`
- Category: `ATTRIBUTION_HIJACKING`
- Status: `WATCH`
- Description:
  - Browser extensions, coupon layers, or late redirects may try to overwrite the true creator attribution.
- Current prevention:
  - first-party `partnerlinks_ref` preserved through cart/order attributes.
  - attribution source/confidence logging.
  - exact `partnerlinks_ref` wins before fallback.
  - low-confidence fallback cannot override exact attribution.
- Regression rule:
  - Exact `partnerlinks_ref` must always win before fallback.

### RISK-019 - Synthetic Commerce Activity

- Severity: `SEV1`
- Category: `SYNTHETIC_COMMERCE`
- Status: `OPEN`
- Description:
  - Fake orders, circular purchases, refund loops, stolen cards, low-quality incentive purchases, or creator/buyer collusion can create artificial commissions.
- Current prevention:
  - payout mode defaults fail-closed.
  - live claimability requires settlement/approval/reserve architecture before activation.
  - pending windows exist in current test-mode lifecycle.
  - refund/reversal/offset states are documented.
- Future prevention:
  - Shopify fraud/risk signal ingestion.
  - suspicious order velocity detection.
  - manual review queue.
  - creator payout holds for new/high-risk patterns.
  - negative balance / `offset_required` model after refunds.
- Regression rule:
  - No live payout should be released just because a conversion exists.

### RISK-020 - Referral / Fake Account Abuse

- Severity: `SEV1`
- Category: `REFERRAL_ABUSE`, `NETWORK_ECONOMICS`
- Status: `OPEN`
- Description:
  - Users may create duplicate creator accounts, fake invited creators, or identity clusters to farm network rewards.
- Important nuance:
  - Self-owned accounts are not automatically bad if real commerce is generated.
  - The real issue is synthetic activity and payout loops.
- Current prevention:
  - no network overrides from self-generated direct sales.
  - no signup/recruitment-only rewards.
  - network rewards only from downstream attributed `platform_fee_amount`.
  - no Level 4+.
- Future prevention:
  - monitor duplicate payout methods, Stripe accounts, tax ids, devices, IPs, and abnormal network/payment patterns.
- Regression rule:
  - Recruitment alone cannot generate PartnerLinks revenue or network payouts.

### RISK-021 - MLM / Recruitment-Only Legal Risk

- Severity: `SEV1`
- Category: `NETWORK_ECONOMICS`, `COMPLIANCE`
- Status: `WATCH`
- Description:
  - Multi-level reward systems become legally dangerous when rewards are based on recruitment rather than real retail commerce.
- Current prevention:
  - no payout for signups alone.
  - network overrides only come from eligible downstream `platform_fee_amount` generated by real attributed sales.
  - hard Level 3 stop.
  - no self-generated network override rewards.
  - direct commission vs network override distinction is documented.
- Regression rule:
  - Network overrides must be funded only by eligible downstream `platform_fee_amount`.

### RISK-022 - Duplicate Webhook / Payment Replay Financial Mutation

- Severity: `SEV1`
- Category: `WEBHOOK_REPLAY`, `PAYOUT_IDEMPOTENCY`
- Status: `WATCH`
- Description:
  - Shopify/Stripe/webhook events may be delivered more than once, creating duplicate conversions, earnings, settlements, or payouts if idempotency regresses.
- Current prevention:
  - Shopify HMAC verification.

  - duplicate/skipped diagnostics.
  - idempotent claim batches.

- Future prevention:

  - brand charge idempotency.
  - refund/reversal idempotency.
- Regression rule:
  - Duplicate webhooks cannot create duplicate financial mutations.

### RISK-023 - Payout Leakage / Unfunded Earnings

- Severity: `SEV1`
- Category: `SETTLEMENT_FAILURE`, `PAYOUT_IDEMPOTENCY`
- Status: `MITIGATED`
- Description:
  - Creators may be paid before brand commission/platform fee settlement is funded.
- Current prevention:
  - `PAYOUT_MODE` fail-closed.
  - production default `claims_disabled`.
  - `sandbox_time_based` allowed only with Stripe test key.
  - accounted earnings are documented separately from funded earnings.
- Future prevention:
  - `settlement_batches` and `settlement_items`.
  - settlement-aware claimability.
- Regression rule:
  - Live claimability cannot be based only on `claimable_at`.

## Small / Mid-Size Platform Fragility Risks

Small platforms, Shopify apps, referral tools, affiliate plugins, and early-stage fintech/creator reward companies often cannot absorb the same failures large companies can. One payout exploit, data leak, fake-account loop, settlement bug, or misleading metric can materially damage trust, cash flow, investor confidence, and brand partnerships.

The following examples are source-backed risk patterns or user-provided research examples. They are included to shape PartnerLinks' internal controls, not as legal conclusions.

### RISK-047 - Affiliate Software SQL Injection

- Severity: `SEV1`
- Category: `SMALL_PLATFORM_FRAGILITY`, `PLUGIN_SQL_INJECTION`, `SQL_INJECTION`, `PARAM_INJECTION`
- Status: `OPEN`
- Real-world pattern:
  - Affiliate/referral plugins such as AffiliateWP and Post Affiliate Pro have had public SQL injection vulnerability reports, including unauthenticated/user-controlled input risks when values were not sufficiently escaped or prepared.
- Source example:
  - SentinelOne CVE/writeup provided in project context: AffiliateWP SQL injection flaw.
- Required prevention:
  - validate `creator_code`, `brand_slug`, `product_slug`, and `partnerlinks_ref`.
  - no raw SQL using route/query params.
  - use parameterized/structured Supabase queries.
  - length-limit public params.
  - escape rendered values.
  - service-role key remains server-only.
  - malicious-input tests for every public referral route.
- Regression rule:
  - `REG-SECURITY-001`: public referral/tracking params cannot alter database queries or expose sensitive data.
